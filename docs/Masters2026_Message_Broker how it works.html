How the Message Broker Works

We started with a user interface and a few hardware classes. Then somebody asked for one more feature. Follow the messages and see why a broker keeps that small change from turning into a rewrite.

01 The problem02 Sending commands03 Feedback04 Adding a feature05 What the broker does not do
CHAPTER 01

It worked fine until we needed to change something

In a tightly coupled program, the UI knows which hardware class to call. That seems convenient, right up until the UI needs to know about every device, every special case, and every replacement.

Direct dependencies

Construct UI → NAX amplifier
Construct UI → NAX IO
Construct UI → Bluetooth

New hardware? Update the UI. Another UI? Duplicate hardware knowledge.

With a broker

Construct UI → Message Broker → NAX classes

The UI asks for a result. A separate class knows how to make that happen. The broker carries the message between them.

Think of SIMPL Windows crosspoints as a useful analogy for separating senders and receivers. It is not a literal crosspoint, though. Our broker routes named messages and their values to subscribers.

CHAPTER 03

Feedback comes back the same way

Commands are only half the story. The hardware reports a change, and the UI needs to update. The hardware class publishes feedback without knowing whether the receiver is a touch panel, a web page, or something we have not written yet.

CHAPTER 04

Now somebody wants another feature

Maybe a different amplifier handles routing differently. Maybe we add another interface. The message contract stays the same, while the class responsible for the new behavior changes.

This is the point of the design. Custom code does not disappear. We put it in the class that owns that responsibility, rather than threading another hardware dependency through the UI.
CHAPTER 05

The broker is not magic

It does not discover hardware capabilities, validate every message, or guarantee that an API method actually works on a particular NAX product. It also does not turn a command into confirmed feedback. Those are still jobs for the application and hardware classes.

The broker owns

Message names, subscriber registration, and delivery of message payloads.

The other classes own

UI events and presentation, routing decisions, device API calls, validation, and actual hardware feedback.

One naming contract matters

"Zone1Source"  // Message name
Analog = 2     // Requested source index

// Both sides must agree on the name and what Analog means.
// The broker cannot guess what we intended.

One final reminder for the lab: the C# help file tells us what the API exposes. SIMPL help and the device web interface help us establish what the hardware really supports. A method compiling is not proof that the device implements it.
